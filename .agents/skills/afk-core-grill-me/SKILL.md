# Grill Me

本 Skill 基于 `mattpocock/skills` 中 `grill-me` / `grilling` 的单问题决策树设计做本地适配，并按 AFK 的确认门与交互协议调整。固定来源、改造说明与 MIT 许可见 `references/UPSTREAM.md`。

## 使用条件

- 用户明确要求 grill、逐题确认或一次只问一个。
- `requirements-explore` 已完成首轮分析，用户选择「一次只问一个」。
- 简单事实查询、只有一个显然决定或需求已经完整时不要强行启用。

## 输入状态

开始前继承或整理：已核实事实、已确认决策、暂定假设和未决问题。可从代码、文档、规则或只读工具获得的事实先自行核实，不把查资料转嫁给用户。

开场「目标」来自**本轮用户真实需求或探索目的**（例如从 `requirements-explore` 的高影响待确认点归纳），只写用户要收敛什么；不要把某一类业务口径（如「要 / 不要」）写成本 Skill 的固定内容或默认目标。

## 逐题循环

1. 按前置依赖和影响大小整理决策树，但不要把整棵树一次抛给用户。
2. 选择当前最影响范围、行为、数据设计或验收的一项。
3. 一次只提出一个需要用户决定的问题，等待回答后再继续。
4. 决策题正文使用下方「拷问题模板」，并遵守全局 `A/B/C…` + `[下一步建议]` 协议；文末仍输出 `[TRACE]`。
5. 用户回答后检查是否解决当前问题、是否与已有决定冲突、是否扩大范围；未解决时继续当前分支，解决后才进入下一项。
6. 进入下一题前，先用一行锁定上一题结论，再出新题；用户接受推荐不等于跳过一致性检查；用户说“都可以”“你决定”也不自动视为已确认。

### 拷问题模板

**首题**可先用一行写本轮用户目标；后续题不要重复开场目标，改为先锁定上一题。

首题：

```markdown
开拷问。目标：{本轮用户真实需求或探索目的，勿套用固定业务口径}。一次只问一个。

**Q1（{短标签，如根决策 / 范围 / 落点}）**

{一句话问题；必要时再补一句背景，不要写成小作文}

A. {短结论}：{该选项考虑的方向，注意不要太长}
B. {短结论}：{该选项考虑的方向，注意不要太长}
C. {短结论}：{该选项考虑的方向，注意不要太长}

[下一步建议] 推荐选 A。推荐理由：{一句简短理由}
```

后续题（先锁定，再提问）：

```markdown
**Q{n-1} 锁定：{上一题确认后的短结论}。**

**Q{n}（{短标签}）**

{一句话问题；必要时再补一句背景，不要写成小作文}

A. {短结论}：{该选项考虑的方向，注意不要太长}
B. {短结论}：{该选项考虑的方向，注意不要太长}

[下一步建议] 推荐选 A。推荐理由：{一句简短理由}
```

- 方向数量按实际互斥结论决定，常为 2～3 个；不为凑格式硬加无效项。
- 选项行格式固定为 `{短结论}：{短方向}`：冒号前是可拍板的结论，冒号后只补该选项在考虑什么，整行保持短，不堆验收细则、例子清单或长定义。
- 「要 / 不要」等措辞仅在用户本轮目标或该题选项本身需要时出现，不是本 Skill 的固定选项模板。
- 必要背景写在问题正文里，且控制在一两句。
- `[下一步建议]` 与推荐字母一致；推荐理由具体、简短。只有取舍不明显会造成误解时，才再补一句主要代价。
- 不要一次抛出多个 `Qn`；下一题等当前题确认后再出，且必须先展示 `Q{n-1} 锁定`。

## 收敛与边界

- 高影响决策已解决或明确保留为风险后，输出共同理解摘要。
- 需求探索一旦收敛，立即结束本 Skill；不要继续追问低影响细节，也不要把逐题节奏带入后续 Plan 或实现。
- 用户明确确认双方已形成共同理解前，不执行实现、不写需求文档、不改项目记忆。
- 由 `requirements-explore` 进入时，完成后返回该 Skill 输出正式《需求对齐稿》，不要自行绕过它的分流规则。
