# 需求探索

**面向未来需求**（目标、非目标、验收）。对齐「系统当前事实」请用 `align-memory`。

## 硬性边界

1. **默认禁止**创建或修改主业务源码、测试、持久化映射、环境配置。选 **D**，或 **B 完成后再说按 Plan 实现** 时除外。
2. **禁止**在本阶段写 `docs/requirements/**`（除非用户选 **A** 或明确说「形成需求文档」）。
3. **禁止**自动改记忆；落盘走 `update-memory` 触发语。
4. **允许**只读：读规则、记忆索引与相关文档，以及只读搜索/只读 Git 查询，用于核对现状。
5. 对齐稿**未确认**前，不得进入实现；须先对齐或用户明确选 **C** 继续澄清。

## 执行步骤

### 1. 建立上下文

- 若相关：先读记忆索引（默认 `docs/ai/README.md`），再按导航下钻。
- 必要时只读搜索代码，用路径/接口/表等支撑「现状」，勿空泛描述。
- 可由代码、文档、规则或只读工具核实的事实，先自行核实；只把目标优先级、业务取舍、风险接受度等决策留给用户确认。

### 2. 单问题决策循环

需求仍不清晰时，在当前会话中维护：

- **已核实事实**：从代码、文档、规则或只读工具确认的现状。
- **已确认决策**：用户已经拍板的目标、范围、业务取舍与风险接受度。
- **暂定假设**：不阻塞主路径、但尚未确认的低影响判断。
- **未决问题**：会改变范围、行为、数据设计或验收方式的选择。

循环执行：

1. 先核实环境中可以发现的事实，不向用户重复询问。
2. 从未决问题中选择当前最影响后续、且前置依赖已解决的一项。
3. 一次只提出一个需要用户决定的问题，并等待回答后再继续。
4. 每个问题必须给出明确推荐：

   **我的建议**：{推荐做法}

   **理由**：{结合已核实事实、已确认决策和当前目标}

   **主要代价**：{会放弃、推迟或增加什么}

5. 用户可以接受、修正或拒绝推荐；推荐不替用户拍板。
6. 回答未解决当前问题时继续围绕它澄清；解决后更新状态，再选择下一项。

### 3. 反迎合与冲突处理

- “全都要”“都可以”“你决定”“以后再说”不能自动视为需求已确认。
- 新回答与已确认决策冲突时，先指出冲突和影响，不进入下一问。
- 范围扩大时，说明新增的业务、数据、交付或验证成本，并要求确定优先级。
- 用户拒绝推荐但没有提供新约束时，继续澄清当前决定。
- 用户接受推荐后，仍检查它与目标、非目标、验收和已有决定是否一致。

### 4. 平衡模式与共同理解确认

必须明确：要解决的问题和用户/调用方、本期目标与非目标、主业务路径、关键业务规则、高影响数据或持久化变化、可观察的成功标准、人工验收主路径、关键风险与难以逆转的决定。

低影响细节可作为暂定假设，不为穷尽细节持续追问。只有高影响内容已确认或明确保留为风险，且目标、范围、主路径、数据变化和验收没有已知冲突时，才输出共同理解摘要。摘要必须列出相关事实、决策、假设与未决风险；用户明确确认双方已形成共同理解后，才进入《需求对齐稿》。

需求已有清晰 PRD、范围和验收标准时，核查现状及冲突后可直接输出共同理解摘要，不强制长时间盘问。

### 5. 输出《需求对齐稿》

用户明确确认共同理解后才输出正式对齐稿（可升版 v1、v2…）。用户说「总结 / 对齐一下」时先输出共同理解摘要；未确认时不要展示 A～D，并继续单问题探索。正式对齐稿**文末必须保留 A～D。**

```markdown
## 需求对齐稿（v1）

### 主题
{一句话}

### 现状
- **代码 / 接口**：{有依据的路径与现行为}
- **数据**：{相关表/字段语义，若有}
- **问题 / 痛点**：{为何要改}

### 目标（本期）
- {可验收条目}

### 非目标（本期不做）
- {条目}

### 风险与约束
- {如：持久化映射须确认、DDL 须人工审核等}

### 暂定假设（若有）
- {不阻塞当前主路径、后续仍需验证的假设}

### 候选领域语言 / 长期决策（若有）
- {值得统一命名、记录为业务规则或进入项目记忆的候选内容；不自动落盘}

### 人工验收（草案，选 A 时迁入需求文档）
- [ ] {主路径场景与预期}
- [ ] {边界或回归}

### 待后续处理（若有）
- {不阻塞本期对齐的后续事项或风险}

### 建议下一步（请选 A / B / C / D）

- [ ] **A. 形成需求文档** → 「形成需求文档：\<slug\>」（走 `requirements-doc`，**默认不编码**）
- [ ] **B. 先拆实现步骤（Plan）** → 「按对齐稿进入 Plan」（走 `planning`，**不写业务代码**）
- [ ] **C. 继续探索** → 补充边界；对齐稿升版
- [ ] **D. 直接实现** → 「按对齐稿直接实现」（须已确认目标与非目标；**不落** requirement.md）
```

### 6. 用户确认后的衔接

| 选项 | Agent 动作 |
| --- | --- |
| 确认对齐稿但未选 A～D | 再次列出 A～D |
| **A** | 启用 `requirements-doc`；默认不编码 |
| **B** | 启用 `planning`；仍不写业务代码 |
| **B 之后**「按 Plan 实现」 | 先说明设计思路、改动范围与影响，再实现 |
| **C** | 回到澄清，升版对齐稿 |
| **D** | 先说明设计思路、改动范围与影响，再实现；不写 requirement.md |

同义：落文档 ≈ A；先 Plan ≈ B；接着聊 ≈ C；开写代码（无文档）≈ D。

## 不要做

- 未选 A/D（或 B→实现）时不要写码或自动写 `docs/requirements/**`。
- 不要省略对齐稿末尾的 A～D。
- 不要一次提出多个待决问题；当前问题未解决时不要跳到下一项。
- 不要把暂定假设写成已核实事实。
- 不要因用户接受推荐而省略一致性检查。
