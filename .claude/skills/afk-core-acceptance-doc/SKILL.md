# 形成测试验收文档

## 定位

`acceptance.md` 回答如何独立执行、交接并记录完整验收。它适合多人验收、较大回归、迁移核对、多环境组合或正式留痕，是可选产物，不是所有需求的必经步骤，也不能代替 `requirement.md` 中不可省略的基本验收标准。

Plan 中每项任务的验证只判断该实施步骤是否正确，`acceptance.md` 则按需求范围组织端到端验收。形成文档不代表已经验收，也不自动授权运行测试、修改代码或开始实现。

## 何时启用（强制）

**视为触发**：形成测试验收文档、编写验收文档、把验收方案写入需求目录、创建 acceptance.md。

**不视为触发**：补充几条验收标准、写测试、运行测试、测试一下、形成需求文档、形成技术方案。不确定是否需要独立落盘时先确认。

Agent 可以在上述复杂验收情形中建议独立文档，但用户未明确触发时不得创建。普通需求直接依据 `requirement.md` 中的验收标准和 Plan 中的验证方式完成检查，不必另建文档。

## 路径与边界

- 文档位置：`docs/requirements/<分支>/<slug>/acceptance.md`。
- 模板位置：`docs/requirements/_template/acceptance.md`（若有）。
- 落盘前按 Git 约定确认目标仓和受保护分支。
- 优先读取同目录 `requirement.md`，按需求范围和验收标准展开；若有 `design.md`，只用它补充迁移、兼容和技术风险场景。
- `acceptance.md` 不得增加业务目标、规则或实现范围；发现规格冲突时先指出并停止把冲突写成验收结论。
- 没有独立需求文档时，明确写出验收依据来自用户提供的 PRD、任务或已确认对话，不自动创建其它文档。

## 最低质量线

按实际需要覆盖：

- 验收范围和必要前置条件；
- 主路径、关键规则、异常与边界场景；
- 数据、权限、兼容、迁移或回归场景（仅在相关时）；
- 每个场景的操作或观察方式，以及可判断的预期结果。

保持轻量：不强制需求编号、测试分层、覆盖率指标或完整测试矩阵。简单场景用短列表即可；需要多人执行或正式留痕时使用表格。

Agent 可以填写场景、操作和预期，但人工验收的**结果列必须留空**，不得代填「通过」，不得勾选验收完成。只有实际运行过自动化验证时，才可在独立的「自动验证记录」中写入命令与真实结果；未运行时删除该节，自动结果不能冒充人工验收结论。

## 执行步骤

1. 确认用户明确要求独立测试验收文档。
2. 确认目标分支、slug 和受保护分支边界。
3. 阅读需求依据及相关技术方案，识别实际风险和回归面。
4. 使用模板创建或更新 `acceptance.md`，省略无关小节。
5. 提示由执行人填写结果；默认结束，不自动运行测试、修改需求、生成技术方案或开始编码。用户在同一轮明确要求「形成验收文档并执行测试」等时，可以继续运行已授权且环境允许的测试，不重复确认，但仍不得代填人工验收结果。

## 不要做

- 把「测试一下」解释为创建验收文档。
- 为了显得完整而堆砌与需求无关的测试分类。
- 重新定义需求范围或用测试文档修补未确认需求。
- 代填人工验收结果或验收状态。
