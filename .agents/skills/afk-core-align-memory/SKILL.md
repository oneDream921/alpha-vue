# 认知对齐

**面向当前事实**（现网怎么用、代码怎么走、记忆是否准确）。面向**未来需求**请用 `requirements-explore`。

## 硬性边界

1. **禁止**创建或修改主业务源码、测试、持久化映射、环境配置。
2. **禁止**创建或修改 `docs/requirements/**`。
3. **禁止**自动修改记忆目录；仅当用户明确说「形成记忆」「更新记忆」「写入记忆」「记录下来」等时，再启用 `update-memory`。
4. **允许**只读核实代码与记忆。
5. 与代码冲突时以代码为准标注差异；记忆与代码冲突时注明「记忆该处可能需要更新」。

## 执行步骤

### 1. 读取已有记忆

- 若相关：先读记忆索引，再按主题下钻 `domains/` / `services/` / `contracts/`。
- 记下与主题相关的既有表述，供对照。

### 2. 请用户陈述认知

可多轮，一次不必全齐：

- **使用侧 / 现网**：谁操作、什么环境、实际行为、历史口径。
- **你认为的业务规则**：流程、状态、是否自动触发某动作。
- **与记忆或同事说法不一致处**（若有）。

使用侧信息 Agent 无法仅从代码推断，应记录为「用户口径」；与可核实代码矛盾时进入对质，勿直接采信。

### 3. 逐条核实

对可核实说法须先读代码再下结论：

| 类型 | 处理 |
| --- | --- |
| 使用侧 / 现网 | 标注「用户口径」；代码无法验证 |
| 与代码一致 | 标注「与代码一致」并给出路径 |
| 与用户说法不一致 | **明确提醒**；表格列出说法 vs 代码，并给代码位置 |
| 记忆与代码不一致 | 指出章节 vs 代码；建议以代码为准更新记忆 |
| 代码有重要逻辑用户未提 | 可选补充，标注「代码侧补充」 |

禁止：未读代码即附和；无依据断言现网；用「可能」「大概」糊弄。

### 4. 输出《认知对齐稿》

```markdown
## 认知对齐稿（v1）

### 主题
{一句话}

### 用户补充（使用侧 / 现网）
- …

### 代码核实（与仓库一致）
- {结论} → `{path}` …

### 与记忆的差异
- 记忆：…
- 代码：…
- 建议：…

### 与用户说法不一致（请裁定）
| 您的说法 | 代码 / 记忆实际情况 | 代码位置 |
| --- | --- | --- |
| … | … | … |

### 拟写入记忆（草案，尚未落盘）
| 目标文件 | 拟增改内容摘要 |
| --- | --- |
| `domains/….md` 等 | … |

### 待您确认
1. …

### 建议下一步
- [ ] 修改对齐稿
- [ ] 确认一致 → 回复 **「形成记忆」** 或 **「暂不写入」**
- [ ] 继续讨论某一条
```

### 5. 对齐确认后的衔接

| 用户意图 | Agent 动作 |
| --- | --- |
| 补充 / 质疑 | 只读核实后升版对齐稿 |
| 确认但对否落盘未表态 | 询问是否形成记忆；**勿自动写文件** |
| 「形成记忆」等 | 启用 **`update-memory`**，只写入已确认的「拟写入记忆」条目 |
| 「暂不写入」 | 结束；对齐稿留在对话中 |
| 误触「开始实现某功能」 | 提醒本 skill 只对齐认知；新需求用 `requirements-explore` |

## 不要做

- 不对齐阶段自动改记忆或源码。
- 不把未裁定争议写入记忆。
- 一轮不要超过 5 个待确认问题。
