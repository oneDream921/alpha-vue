# 需求探索

面向未来需求（目标、非目标、验收）；对齐系统当前事实使用 `align-memory`。

## 硬性边界

- 默认只读，不创建或修改主业务源码、测试、持久化映射、环境配置或 `docs/requirements/**`。
- 不自动修改记忆；需要落盘时使用 `update-memory`，需求文档使用 `requirements-doc`。
- 对齐稿未确认前不进入 Plan、需求文档或实现；只读检查、搜索、文档和 Git 查询可以使用。

## 首轮分析

先阅读相关记忆入口和项目规则，再核实代码、文档、接口、数据和配置。维护四类状态：

- 已核实事实；
- 已确认决策；
- 暂定假设；
- 未决问题。

首轮至少覆盖目标与非目标、主路径、关键规则、数据变化、异常原则、成功标准、人工验收和不可逆风险。集中列出全部高影响待确认点，不把低影响细节包装成问题。

推荐结构：

```markdown
## 需求初析
### 已理解的目标
### 已核实的现状
### 高影响待确认点
### 暂定假设 / 风险（若有）
```

有两个及以上待确认点时，提供两种入口：

- `A. 一次只问一个：按依赖逐题确认`
- `B. 一次回答多个：本轮集中回复一批`

只有一个待确认点时直接列实际选项；没有待确认点时直接进入共同理解摘要；用户已指定模式时不重复询问。

## 继续方式

### 一次只问一个

启用 `grill-me`，让它逐题处理高影响未决问题，收敛后把状态和结论交还本 Skill。

### 一次回答多个

每批最多 3～5 个高影响问题；每题单独编号、列短选项、给推荐和一句理由。用户回复后检查遗漏、依赖、冲突和范围变化，再决定补问或收敛。

## 反迎合与收敛

- “全都要”“都可以”“你决定”“以后再说”不自动视为确认。
- 新回答与已确认决策冲突时，先指出影响；范围扩大时先确认优先级。
- 用户接受推荐后仍检查目标、非目标、验收和已有决定是否一致。
- 高影响内容已确认或明确保留为风险，且目标、范围、主路径、数据和验收没有已知冲突时，输出共同理解摘要。
- 用户说“总结 / 对齐一下”时先输出摘要；用户明确确认共同理解后，才输出正式《需求对齐稿》。

## 《需求对齐稿》

```markdown
## 需求对齐稿（v1）
### 主题
### 现状
- **代码 / 接口**：
- **数据**：
- **问题 / 痛点**：
### 目标（本期）
### 非目标（本期不做）
### 风险与约束
### 暂定假设（若有）
### 候选领域语言 / 长期决策（若有）
### 人工验收（草案）
- [ ]
### 待后续处理（若有）
### 可选方向（若有）
[下一步建议] {推荐方向与一句理由；无可执行建议时写“无”}
```

需求确认后，只列符合用户当前意图的真实动作：继续探索、形成用户明确要求的文档、先做实施规划或直接实现，不把 `requirement.md`、`design.md`、`acceptance.md` 的组合展开成工作流分支。文档只是按需留档，不自动授权规划、实现或测试；用户同一轮已明确要求组合动作时连续完成，不重复确认。

完成一次后续动作后，本 Skill 结束；后续 Skill 不继承本阶段的问答节奏。用户已明确要求实现时，简单低风险任务可以直接实施；复杂、跨模块或涉及迁移、兼容、回退的任务先用 `planning` 形成 Plan，再连续实现。
