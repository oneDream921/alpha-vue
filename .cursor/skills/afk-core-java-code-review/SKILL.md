# Java Code Review

默认只读、只报可证实的 **High / Medium** 风险点。先核对“是否做对了”，再评“实现是否可靠”；不默认改代码、巡检风格或给合并结论。

## 边界

- 仅用户明确说「帮我修」「review 并修复」等时才改。改前说明设计思路、范围和影响；涉及 SQL / Mapper、删除逻辑或大范围数据变更时仍先确认。
- 本 Skill 只负责 Java 改动，不审查混合变更中的前端部分；项目存在对应前端 Skill 时组合使用，否则按项目规则另行审查。
- 用户要复现既有异常并定位根因时使用 `debugging`；要形成实施方案时使用 `planning`。评审中发现问题不自动切换为修复、调试或规划。
- 安全 Rule 的确认和禁止项始终生效。规格不清不代表可以放宽授权、数据或安全边界。

## Workflow

### 1. 锁定审查范围

先产出本轮审查清单，只围绕清单和验证风险所必需的调用方、契约与测试：

1. 用户点名的文件、目录、PR 或 commit 优先。
2. 否则在目标 Git 仓根读取 `git status` 与 staged / unstaged diff；仅用户要求时纳入未跟踪文件。
3. 多仓且目标不明确时，先列候选仓及改动摘要并询问；不得把 workspace 根当作 Git 仓。
4. 无改动且用户未指定对象时，询问审查目标，不猜测全仓范围。

### 2. 核对预期行为

先从用户说明、点名的需求 / 计划、验收标准、项目 Rule、API / 安全文档、调用契约和既有测试中提取与本次改动直接相关的预期。用一句话记录审查目标，并优先检查：

- 必需行为是否遗漏或解释错误；
- 边界、失败路径和兼容承诺是否满足；
- 是否出现无需求支撑的功能扩张、过早抽象或额外复杂度。

没有可靠规格时，明确写「规格依据不足」，再依据调用方、邻近实现和现有测试审查；不要虚构要求，也不要因此阻塞纯代码风险检查。若实现明显偏离目标，先报告该风险，不在可能应删除的代码上制造重构噪音。

### 3. 加载必要上下文

1. 尝试读取项目记忆索引（默认 `docs/ai/README.md`），按改动域下钻，不加载整套记忆。
2. 记忆缺失或不可读时转为纯代码审查；记忆与代码冲突时以代码为准，并指出冲突。
3. 读取相关模块的邻近实现和项目规范，判断分层、依赖方向、公开契约与既有模式；项目专有框架规则以项目内容为准，不固化为 Core 假设。

记忆是增强信号，不是前置门禁。

### 4. 先规格、后质量审查

| 类别 | 只检查会形成 High / Medium 风险的内容 |
| --- | --- |
| 规格 | 遗漏、误解、破坏验收条件、范围蔓延或无依据抽象 |
| 架构 | 职责错层、依赖倒置、绕过既有入口、公开契约或兼容性破坏 |
| 安全 | 注入、越权、敏感信息、不可信输入；安全风险宁可报 Medium，不降为 Low |
| 正确性 / 数据 | 分支、空值、状态、并发、事务、SQL、批量写入、逻辑删除和边界缺陷 |
| 性能 | 可落到真实执行路径的 N+1、无界查询 / 循环、阻塞或明显资源泄漏；说明触发条件，不做猜测性优化 |
| 测试 | 关键行为、失败路径、权限或回归缺少有效保护；检查断言是否验证行为、Mock 是否掩盖集成风险 |

严重度按影响而非类别判定：**High** 表示存在可直接触发的越权、数据损坏 / 丢失、广泛不可用等严重后果；**Medium** 表示有可信触发路径，会造成错误行为、安全或性能退化、契约破坏，并应在交付前处理。纯维护成本、个人偏好或仅可能在未来发生的问题不构成 Medium。

测试缺口只有在可能放过 High / Medium 行为风险时才作为发现；不以覆盖率数字、缺少某类测试或个人偏好单独报问题。

### 5. 校验证据与噪音

每条发现必须：

- 优先指向实现 `file:line`。完全缺失的行为改为引用规格 `file:line` 或需求标识，并在存在时补充最接近的实现入口；不得为了满足格式而虚构代码位置；
- 给出最小、可操作的修复方向，但不强制附大段示例代码；
- 区分事实与待确认假设。证据不足时继续只读核实，不能核实则不升级成风险点。

不报 Minor / nit、命名与格式偏好、linter / formatter 已覆盖的问题、泛化重构建议、强制赞美或与风险无关的知识展示。用户明确要求「顺便查规范」时，才在风险点之后单列规范偏差，并对照项目 `.project-agent/rules`。

## 输出

```markdown
## 风险点

审查范围：`path1`, `path2`, ...（N 个文件）
规格依据：`来源` / 规格依据不足

### High
- `path:line` - 风险、触发条件与影响。建议：最小修复方向。

### Medium
- `path:line` - 风险、触发条件与影响。建议：最小修复方向。
```

默认每条发现使用一个紧凑段落；仅证据链复杂时再展开「证据 / 影响 / 建议」，并省略没有发现的严重度标题。没有发现时写：`本轮改动未发现 High/Medium 风险点。审查范围：N 个文件。规格依据：...`。不要输出 Approve / Request Changes / Verdict。正文结束后仍按项目交互协议输出 `[下一步建议]` 与 `[TRACE]`，技能字段填 `java-code-review`。
