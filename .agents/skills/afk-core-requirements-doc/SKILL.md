# 形成需求文档

## 定位

`requirement.md` 是需求范围的唯一依据，回答为什么做、做什么、不做什么以及如何判断完成。适合需要跨会话复用、多人协作、正式留痕或范围容易漂移的需求；简单任务没有明确留档要求时不强制创建。

技术方案的稳定结论可以按需写入 `design.md`，需要独立执行、交接或留痕的完整验收可以按需写入 `acceptance.md`；没有独立文档时，关键技术风险仍需在 Plan 中解决，需求验收标准仍不可省略。形成 `requirement.md` 只表示保存需求基线，不自动授权规划、生成其它文档或开始实现。

## 路径约定

| 产物 | 位置 |
| --- | --- |
| 需求文档 | `docs/requirements/<分支>/<slug>/requirement.md` |
| 文档模板 | `docs/requirements/_template/requirement.md`（若有） |
| 索引 | `docs/requirements/README.md` |

**分支归档名**：在主业务 Git 仓目录执行 `git rev-parse --abbrev-ref HEAD`。多仓 workspace 先问用户哪个是主仓，**不得**猜测。Detached HEAD 时与用户约定归档名，或用 `_detached/`。`<slug>` 为 kebab-case 英文短名。

**生产分支上禁止落盘（强制）**：若当前等于项目 Rule 的「生产分支」（未配置时兜底 `main` / `master`），且用户未明确要求就地归档，则**不要**写入 `docs/requirements/`；先按 Git 约定提示迁出专题分支，待用户确认已切分支后再落盘。

## 何时启用（强制）

**视为触发**：形成需求文档、编写需求文档、写需求文档、把需求记到 docs/requirements、按需求目录规范建文档。

**不视为触发**：仅讨论或总结需求、形成技术方案、形成测试验收文档、改代码、评审。不确定是否落盘时先确认。

## 最低质量线

每份需求必须清楚回答以下问题，不能为了精简而省略关键结论：

- 为什么做；
- 本期做什么、不做什么；
- 主路径、关键规则和必要的异常原则是什么；
- 存在哪些实际影响、风险、假设或未决项；
- 如何通过可观察结果判断需求完成。

只保留与当前需求有关的内容，不生成空小节，不为套模板虚构信息。缺少高影响结论时回到 `requirements-explore`；允许保留的低影响未知项必须明确标为假设或待确认，不能写成事实。

验收标准写成“场景 + 可观察预期”，不能只写“功能正常”“测试通过”或把实现任务当作验收。简单需求使用短列表，不强制表格、编号或状态机。

## 内容边界

- `requirement.md` 可以记录接口、数据和状态变化的业务语义，但不默认写文件清单、类名、详细 DDL、技术方案比较、发布步骤或完整测试矩阵。
- 若技术复杂度、迁移、兼容、灰度、回退或跨模块风险需要独立说明，建议进入 `planning`；只有用户明确要求「形成技术方案」时才落盘 `design.md`。
- 若验收需要多人执行、较大回归、迁移核对、多环境或正式留痕，可建议形成测试验收文档；只有用户明确要求时才使用 `acceptance-doc`。
- 可选文档不得重新定义或扩大 `requirement.md` 的范围。需求更新时，只检查并提示现有 `design.md`、`acceptance.md` 的受影响内容，不自动重写。

## 从对齐稿映射

| 对齐稿 | requirement.md |
| --- | --- |
| 主题 + 现状 + 痛点 | 背景 |
| 目标 + 非目标 | 目标与范围 |
| 主路径 + 关键规则 + 异常原则 | 需求说明 |
| 数据变化的业务语义 + 风险 + 假设 | 影响、风险与假设 |
| 人工验收草案 + 成功标准 | 验收标准 |
| 未决风险 | 待确认事项（若有） |

## 执行步骤

1. 确认当前分支：若在生产分支（或其它受保护分支）且用户未要求就地归档，先提示迁出，**停止落盘**。
2. Read `docs/requirements/README.md`；若有 `_template/requirement.md` 可参考其布局，但本 Skill 的内容边界优先，旧模板中冲突的实现清单、详细 DDL 或状态表不应继续带入。
3. 确定分支归档名与 slug；新建 `docs/requirements/<分支>/<slug>/`。
4. 将已确认的对齐内容写入 `requirement.md`，按需省略没有内容的可选小节。
5. 增量更新 `docs/requirements/README.md` 索引；索引只链接主需求文档，不要求登记可选文档状态。已有索引包含「状态」等自定义列时保留原表结构、对应值留空，不借机重写。
6. 提示用户复核需求文档；默认结束，不自动生成其它文档、进入 Plan 或开始编码。用户在同一轮明确要求「形成需求文档并实现」「按文档开发」等时，可以在落盘后继续，不重复确认。

## 不要做

- 未触发时不写 `docs/requirements/**`。
- 在生产分支（或其它受保护分支）上落盘需求（除非用户明确要求就地归档）。
- 把对话中的需求总结直接当作落盘授权。
- 用户未明确要求时，不得自动创建 `design.md`、`acceptance.md`、SQL 或业务代码。
- 不得在 `requirement.md` 代填测试结果，或因模板升级批量改写历史文档。
