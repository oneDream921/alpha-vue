# S0-05 兼容性决策评审

## 1. 评审结论

S0-01 至 S0-04 的基线、隔离 Spike、真实运行和回滚证据完整，第一期可以进入 G0
人工验收。总体结论为：

- **第一期：`GO WITH CONSTRAINTS`**。范围仅为基础设施瘦身、Redis 干净迁移、
  类型化配置、`clientId` 完整会话闭环、日志元数据、存储整理和必要前端配套。
- **第二期：按收益触发**。Spring Boot Admin 与 VXE 单页试点虽通过兼容验证，
  但没有真实需求时不实施。
- **三期：保留轻量基础能力**。日志等清理由应用内 Spring 定时任务承担。
- **SnailJob、Lock4j：`DEFER`**。不属于已排期交付，不预建模块、配置、数据库或页面。
- **G0 当前状态：`PASSED`**。自动证据、人工验收和用户确认均已完成；方案文档提交
  后可按独立分支策略开始 P1-01。

## 5. 停止条件与回滚边界

### 5.1 通用停止条件

出现以下任一情况，当前任务停止，不继续叠加后续改造：

- 依赖树出现未评审的 Boot 3 Starter 或重复实现；旧 Redis Client 仅允许存在于
  P1-03 到 P1-04 的不可发布迁移窗口，超过该边界即停止；
- 当前任务直接相关的针对性检查失败，或 G1/G2 收口时后端
  test/package、前端 typecheck/test/lint/format/build 任一失败；
- 真实 HTTP 登录、权限、文件或 Redis 冒烟失败；
- 会话、缓存或日志产生无法解释的数据格式；
- 必须扩大一期范围才能让当前任务成立；
- 安全边界要求记录请求体、凭据、验证码、上传正文或敏感返回值。

### 5.2 回滚原则

- 每个 P1 任务形成可独立审阅和回退的变更单元；是否提交仍需用户明确确认，不在失败
  任务上继续开发。
- P1-01、P1-02 通过恢复该任务依赖和配置回滚，不触碰业务数据。
- P1-03 未进入数据迁移前可直接移除 Redisson；进入 P1-04 后不做双读双写回滚，
  而是恢复代码、按迁移清单清理本次创建的新 `alpha:*` Key、使会话失效并重新登录。
- `clientId` DDL 只通过追加 Flyway 落地；回滚使用补偿迁移，不修改已执行脚本。
- 存储 Provider 切换不自动迁移历史文件，失败时恢复原 Provider 配置。
- 不回滚或覆盖用户已有未提交修改。

## 8. 后续重评触发条件

| 能力 | 允许重评的最小触发条件 |
| --- | --- |
| Spring Boot Admin | Actuator 无法满足运维排查，且存在独立部署、认证和网络边界需求 |
| VXE Table | Ant Table 在一个真实复杂列表中无法满足固定列、列设置或宽表交互 |
| SnailJob | 应用内任务无法满足多实例协调、可靠重试或可视化运维，并能承担独立服务与 Schema |
| Lock4j | 出现数据库唯一约束、幂等键和直接 Redisson 锁都不能清晰解决的跨实例互斥场景 |
| Snowflake ID | 正式投产或多实例写入前，数据库 ID 已不能满足容量或生成边界 |

每次重评都必须重新检查当前版本、Spring Boot 兼容性、安全边界、故障恢复和退出成本，
不得直接沿用本次 Spike 的历史版本结论。
