# 需求探索

**面向未来需求**（目标、非目标、验收）。对齐「系统当前事实」请用 `align-memory`。

## 硬性边界

1. **默认禁止**创建或修改主业务源码、测试、持久化映射、环境配置。用户确认对齐稿并明确选择实现后除外。
2. **禁止**在本阶段写 `docs/requirements/**`（除非用户明确选择「形成需求文档」）。
3. **禁止**自动改记忆；落盘走 `update-memory` 触发语。
4. **允许**只读：读规则、记忆索引与相关文档，以及只读搜索和只读 Git 查询，用于核对现状。
5. 对齐稿未确认前不得进入实现、Plan 或需求文档；用户可明确要求继续探索。

## 执行步骤

### 1. 建立上下文

- 若相关，先读记忆索引（默认 `docs/ai/README.md`），再按导航下钻。
- 必要时只读搜索代码，用路径、接口、表或配置支撑「现状」，勿空泛描述。
- 可由代码、文档、规则或只读工具核实的事实，先自行核实；只把目标优先级、业务取舍和风险接受度等决策留给用户确认。
- 在当前会话中维护四类状态：
  - **已核实事实**：从环境中确认的现状。
  - **已确认决策**：用户已经拍板的目标、范围和取舍。
  - **暂定假设**：不阻塞主路径、但尚未确认的低影响判断。
  - **未决问题**：会改变范围、行为、数据设计或验收方式的选择。

### 2. 首轮深度初析

首轮不得直接丢出一个零散问题，也不要用「待确认：补充某某正式设计」把分析责任留到下一轮。先充分核查现状并推演需求，至少覆盖：问题与用户、目标与非目标、主业务路径、关键规则、数据或持久化变化、异常原则、成功标准、人工验收和难以逆转的风险。

首轮正文按需展示：

```markdown
## 需求初析

### 已理解的目标
- {当前理解}

### 已核实的现状
- {事实与依据}

### 高影响待确认点
1. {确认点及其影响；只描述决策主题，不在这里展开盘问}
2. {确认点及其影响}

### 暂定假设 / 风险（若有）
- {内容}
```

必须集中展示全部高影响待确认点，让用户先看到完整决策范围；低影响细节不为凑数量列入。

根据待确认点数量决定入口：

- 有两个及以上待确认点：列出下面两个方向，每个方向独占一行。

  `A. 一次只问一个：启用 grill-me，根据上一项答案动态选择下一问。`

  `B. 一次回答多个：本轮集中列出一批简洁问题，用户统一回复。`

  `[下一步建议] 推荐选 A。理由：后续问题可根据上一项答案动态调整，减少遗漏和前后冲突。`

- 只有一个待确认点时，不额外询问回答模式，直接把该问题及实际可选方向列清楚，并给出推荐与一句理由。
- 没有待确认点时，不展示回答模式，直接进入共同理解摘要。
- 用户已经明确指定回答模式时，尊重选择，不重复询问。

### 3. 按用户选择继续

#### 一次只问一个

启用 `grill-me`，把四类探索状态交给它；由它按依赖和影响一次只处理一个决策。逐题完成并形成共同理解后返回本 Skill 收口。

#### 一次回答多个

- 每批最多 3～5 个高影响问题；仍有缺口再开下一批，不一次倾倒完整问题库。
- 每个问题单独编号，问题下的可选方向逐行展示，避免多层嵌套和长表格。
- 每个问题都给出推荐答案和一句简短理由；只有关键取舍容易误解时才补一句主要代价。
- 最后的 `[下一步建议]` 推荐一组明确答案，例如「推荐选 1A、2B、3A」，理由保持简短。
- 用户统一回复后，先检查遗漏、依赖和冲突，再决定补问或进入共同理解摘要。

### 4. 反迎合与冲突处理

- “全都要”“都可以”“你决定”“以后再说”不能自动视为需求已确认。
- 新回答与已确认决策冲突时，先指出冲突和影响，不进入下一问。
- 范围扩大时，说明新增的业务、数据、交付或验证成本，并要求确定优先级。
- 用户拒绝推荐但没有提供新约束时，继续澄清当前决定。
- 用户接受推荐后，仍检查它与目标、非目标、验收和已有决定是否一致。

### 5. 共同理解确认

只有高影响内容已确认或明确保留为风险，且目标、范围、主路径、数据变化和验收没有已知冲突时，才输出共同理解摘要。摘要列出相关事实、决策、假设与未决风险；用户明确确认双方已形成共同理解后，才进入《需求对齐稿》。

需求已有清晰 PRD、范围和验收标准时，核查现状及冲突后可直接输出共同理解摘要，不强制选择回答模式或长时间盘问。

### 6. 输出《需求对齐稿》

用户明确确认共同理解后才输出正式对齐稿（可升版 v1、v2…）。用户说「总结 / 对齐一下」时先输出共同理解摘要；未确认共同理解时，不展示形成需求文档、进入 Plan 或直接实现等后续方向。

```markdown
## 需求对齐稿（v1）

### 主题
{一句话}

### 现状
- **代码 / 接口**：{有依据的路径与现行为}
- **数据**：{相关表或字段语义，若有}
- **问题 / 痛点**：{为何要改}

### 目标（本期）
- {可验收条目}

### 非目标（本期不做）
- {条目}

### 风险与约束
- {内容}

### 暂定假设（若有）
- {不阻塞当前主路径、后续仍需验证的假设}

### 候选领域语言 / 长期决策（若有）
- {值得统一命名、记录为业务规则或进入项目记忆的候选内容；不自动落盘}

### 人工验收（草案）
- [ ] {主路径场景与预期}
- [ ] {边界或回归}

### 待后续处理（若有）
- {不阻塞本期对齐的后续事项或风险}

### 可选方向
A. {当前实际可走的动作}
B. {另一项当前实际可走的动作；没有则省略}

[下一步建议] 推荐选 {选项}。理由：{一句简短理由}
```

只列当前实际可走的方向，数量可以为零、一个或多个，并按展示顺序重新编号；不要为了沿用固定 A/B/C/D 语义而补齐四项。候选动作包括：形成需求文档、先进入 Plan、继续探索、直接实现。若没有后续动作，省略「可选方向」并写 `[下一步建议] 无`。

### 7. 用户确认后的衔接

- 选择「形成需求文档」：启用 `requirements-doc`，默认不编码。
- 选择「先进入 Plan」：启用 `planning`，仍不写业务代码。
- Plan 完成后用户再明确要求实现：先说明设计思路、改动范围与影响，再实现。
- 选择「继续探索」：回到确认流程，对齐稿升版。
- 选择「直接实现」：先说明设计思路、改动范围与影响，再实现；不自动写 requirement.md。

按方向名称理解用户选择，字母只服务当前一轮展示，不建立跨轮固定映射。

需求探索在共同理解确认并完成一次后续分流后结束。后续 Skill 不继承逐题或批量确认模式；需求、范围和授权未发生变化时，Agent 应连续完成 Plan、文档或实现，不再要求用户逐步决定。只有实施中暴露出新的高影响业务取舍，才回到需求确认；一般技术细节由 Agent 按现有规则和代码事实自行判断。

## 不要做

- 用户未明确选择形成需求文档或实现时，不要写业务代码或 `docs/requirements/**`。
- 不要首轮只抛一个未经整体分析的问题。
- 不要在用户选择逐题模式后一次提出多个待决问题。
- 不要把暂定假设写成已核实事实。
- 不要因用户接受推荐而省略一致性检查。
- 不要输出冗长推荐理由或为格式凑满四个方向。
- 不要把需求探索的问答节奏延续到已经确认的 Plan 或实现阶段。
