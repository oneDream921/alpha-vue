# Alpha Vue 框架现代化实施计划

## 1. 执行原则

本计划服务于 Alpha Vue 的分阶段改造。执行时必须遵守以下规则：

1. 一次只执行一个任务，不允许自动串行进入下一任务。
2. 每个任务开始前先读取相关现状代码、现行文档和本目录设计文档。
3. 任务范围外的代码、配置、依赖和格式不得顺带调整。
4. 发现工作区已有修改时必须保留，并基于现状继续工作。
5. 开发过程中只运行与改动直接相关的检查；里程碑和阶段结束时再执行完整验证。
6. 涉及安全、会话、序列化、数据迁移或运行时依赖替换时，必须由强模型复核。
7. 未通过当前任务的停止条件，不得开始下一任务。
8. 目标设计文档不能提前覆盖描述当前实现的正式文档；只有能力实际落地后，才同步更新正式文档。

### 1.1 Git 分支与提交策略

方案文档经用户确认后先作为独立文档提交进入 `main`，形成后续实施基线。生产代码采用
“一个任务、一个短生命周期分支”的方式开发，不建立覆盖整个一期的长期集成分支：

1. 每个任务从最新、干净的 `main` 创建分支，命名为
   `codex/<任务编号>-<主题>`，例如 `codex/p1-01-hikari`。
2. 分支只能包含当前任务必要的代码、配置、测试和已落地正式文档，不夹带下一任务。
3. 开发中形成可独立审阅的提交；未获得用户明确“确认提交”前，不执行提交或合并。
4. 完成针对性验证、强模型复核和用户验收后，才允许合并回 `main`。
5. 合并后以更新后的 `main` 作为下一任务起点，不从旧任务分支继续分叉。
6. 任务失败或触发停止条件时保留诊断证据，回退或废弃当前分支，不污染 `main`。
7. G1、G2 等阶段门禁仍在 `main` 的已合并状态上执行完整验证，单个任务通过不代表
   整个阶段通过。

推荐一期分支顺序从 `codex/p1-01-hikari` 开始；每次只创建当前已获授权的分支。

## 2. 模型分工

### 2.1 标准执行模型

适合执行边界清晰、验收条件明确的任务，例如：

- 依赖替换后的配置清理；
- DTO、VO、Mapper XML、前端类型和接口适配；
- 已确定方案的页面改造；
- 文档同步和固定命令验证。

执行模型必须逐项回报：

- 实际修改的文件；
- 与计划不同的地方；
- 已运行的验证及结果；
- 未验证内容；
- 是否触发停止条件。

### 2.2 强模型评审

以下节点必须由强模型执行或复核：

- Spring Boot 4 兼容性结论；
- Redisson 编解码和数据兼容方案；
- clientId 会话原子性、并发和踢下线语义；
- 审计日志字段边界和脱敏策略；
- Redis 管理写操作的权限与保护；
- VXE Table 是否扩大使用范围；
- SnailJob、Lock4j 和 ID 策略是否进入正式基线；
- 每个阶段的最终验收结论。

5. 将 clientId 和设备摘要写入会话元数据及登录日志。
6. 明确旧客户端兼容窗口；正式启用后不得静默补默认值。
7. 回滚只允许追加补偿迁移，不修改已执行脚本。

### P1-07 同 client 单会话原子控制

**目标**

实现“不同 client 可并存、同一用户同一 client 只保留一个有效会话”。

**执行步骤**

1. 设计用户、clientId、token 和会话索引关系。
2. 使用 Redis 原子操作完成新会话占位和旧会话失效。
3. 处理并发登录、登录中断、TTL 过期和异常回滚。
4. 保留不同 clientId 的有效会话。
5. 禁用或删除用户时失效其全部 client 会话。
6. 注销只结束当前会话，并保留正确的审计操作人。

**强制测试**

- 同用户同 client 并发登录；
- 同用户不同 client 并存；
- 旧 token 失效；
- 当前 token 注销；
- 用户禁用和删除；
- Redis 短暂异常。

### P1-08 在线用户与定向下线

**目标**

在线用户以会话为粒度展示，并支持精确踢下线。

**字段**

- 用户、账号、部门；
- clientId、deviceId/deviceName；
- token 会话标识的安全摘要；
- IP、地点、浏览器、操作系统；
- 登录时间、最后访问时间、过期时间。

**执行步骤**

1. 在线列表只从受控会话索引读取，不扫描无边界 keyspace。
2. 踢下线接口必须按目标会话执行，不误伤其他 client。
3. 权限、审计和二次确认必须完整。
4. 前端表格继续使用现有 Ant Design Vue Table。

### P1-09 登录日志与操作日志元数据增强

**目标**

增强排障信息，同时维持敏感数据边界。

**第一期允许记录**

- 操作人、模块、动作、结果、耗时、traceId；
- IP、IP 归属地、浏览器、操作系统、clientId、设备摘要；
- 路径、HTTP 方法、响应状态；
- 成功/失败、业务错误码和有界异常摘要。

**第一期禁止记录**

- Token、Cookie、密码、验证码；
- 文件正文和二进制内容；
- secret、key 等敏感字段；
- 所有请求参数、请求体和响应体；
- 签名 URL 和内部配置值。

**执行步骤**

1. 集中实现 UA 解析、IP 提取、内网判断和 ip2region 查询。
2. 为代理头建立可信代理配置，禁止无条件信任客户端头。
3. 通过本任务的追加 Flyway 迁移增加已确认的登录与操作日志快照字段、必要索引和
   长度约束；迁移脚本须人工审核。
4. 对异常摘要建立脱敏和长度上限。
5. 对日志写入失败采用隔离策略，不能影响主业务结果。
6. 更新日志详情页面，但不引入请求参数、请求体或响应体记录。

### P1-10 轻量 SQL 监控整理

**目标**

删除 p6spy 目标，增强现有进程内、无参数、有界 SQL 摘要。

**执行步骤**

1. 记录 SQL 模板摘要、耗时、Mapper 标识、traceId 和时间。
2. 不记录绑定参数，不提供慢 SQL 全量持久化。
3. 使用固定容量和过期策略，避免内存无界增长。
4. 提供阈值、启停和最大条数配置。
5. 验证异常 SQL 不泄露敏感数据。

### P1-11 存储 Provider 基线整理

**目标**

保持 `StorageProvider` 抽象，开发环境默认本地存储，Compose/生产推荐 MinIO。

**执行步骤**

1. 固化上传、读取、删除、元数据和公开/私有访问契约。
2. 保留 local 与 MinIO 两个真实实现。
3. 配置切换不能要求修改业务代码。
4. 校验文件大小、扩展名、内容签名、路径穿越和访问权限。
5. OSS/COS/S3 只保留扩展说明，不加入空实现或无用依赖。

### P1-12 前端认证与服务层整理

**目标**

在不迁移整套 Vben 工程的前提下，形成清晰的前端结构和认证闭环。

**执行步骤**

1. 统一请求客户端、错误处理、Token 注入和登录失效处理。
2. 登录请求固定携带 `pc-admin` clientId。
3. 建立模块化 API、类型和页面目录边界。
4. 修复接口字符集和日期展示的一致性。
5. 保留现有 UI 技术栈，样式新增优先使用 UnoCSS。
6. 为在线用户、登录日志和操作日志增加响应式布局。

### P1-13 第一期收口

**执行步骤**

1. 更新 README、架构、安全、运维和开发规范中已经落地的内容。
2. 删除失效依赖、配置、端点、文档和死代码。
3. 运行完整后端与前端验证。
4. 执行真实登录、会话、日志、缓存、文件和数据库冒烟。
5. 由强模型进行安全、兼容和范围复核。

**阶段门禁**

- `G1`：基础依赖与基础设施；
- `G2`：clientId 会话、日志和存储闭环。

## 5. 第二期：管理体验与可观测性增强

### P2-00 能力触发决策

第二期不是固定功能包。每次只选择一个有真实问题、收益指标和回退方案的能力，经用户
确认后执行对应任务；其余任务记为 `N/A`，不得为凑齐阶段清单而实施。若没有能力被
触发，则不创建第二期变更，也不执行 G3。

### P2-01 VXE Table 单页试点

仅在 Ant Table 已出现明确复杂列表瓶颈时，选择在线用户或操作日志中的一个页面试点，
验证列设置、固定列、响应式、虚拟滚动、测试和维护成本。实施前必须使用 Alpha 当时
的 lockfile 和 TypeScript 版本重跑兼容验证；S0-04 的 TypeScript 5.8.3 结果不能替代。

### P2-02 表格技术决策

由强模型依据试点结果决定：

- 仅复杂页面使用 VXE；
- 形成受控业务表格组件；
- 停止引入并回到 Ant Design Vue Table。

不得在结论前全量迁移。

### P2-03 Redis 监控增强

在只读概览基础上增加：

- Redis 基本信息；
- 内存结构和趋势图；
- 命令统计图；
- 受限 SCAN；
- 单键删除二次确认。

禁止建设通用 Redis 控制台。

### P2-04 缓存展示分级

建立可配置的 `HIDDEN`、`MASKED`、`PLAIN` 展示策略。默认 `MASKED`，敏感命名空间必须 `HIDDEN`，配置只能引用代码注册项。

### P2-05 跨设备用户偏好

新增 `sys_user_preference`，只同步经过白名单注册的主题、密度、列布局等偏好。偏好必须有 schema 版本、大小限制和迁移策略。

### P2-06 审计详情增强

安全评审通过后，才允许增加更丰富的请求/响应摘要：

- 仅对白名单接口和字段生效；
- 必须结构化脱敏和截断；
- 响应默认只保留状态摘要；
- 导出、查看和保留周期受权限控制。

### P2-07 Spring Boot Admin

在 Spike 为 `GO` 且确有运维需求时接入。管理端必须独立鉴权，敏感 Actuator 端点默认关闭或脱敏。

### P2-08 第二期收口

只对已触发能力运行对应验收；阶段收口时执行完整构建、相关桌面与移动端验收及必要的
安全复核。未触发能力记录 `N/A`。

**阶段门禁：G3**

## 6. 第三期：受控定时任务与生产能力

### P3-01 应用内基础定时任务

使用 Spring 定时能力，优先提供以下受控任务：

- 登录日志和操作日志按保留策略清理；
- 临时文件清理；
- 存储元数据一致性报告；
- 过期会话索引修复；
- 运行健康摘要。

默认只启用风险低且幂等的清理任务。删除型任务必须支持 dry-run、批次上限和审计。

### P3-02 SnailJob 重评

当前为 `DEFER`，不默认实施。只有应用内任务无法满足真实的多实例协调、可靠重试或
可视化运维需求时，才补齐失败链路 Spike 并重新进行 `GO/DEFER/REPLACE` 评审。
若转为 `GO`，第一版直接使用 SnailJob 管理界面，不在 Alpha Web 复制任务中心。

### P3-03 Lock4j 重评

只有出现明确的跨实例并发业务场景时才引入。若 SnailJob 或数据库唯一约束已能解决，不重复增加锁抽象。

### P3-04 ID 策略决策

在正式投产或需要多实例写入前决定继续使用数据库 ID，或切换雪花 ID。切换前必须处理 JavaScript 长整数、worker 配置、迁移和回滚。

### P3-05 第三期收口

验证已采用的任务能力、清理任务、恢复能力、生产配置和升级文档。SnailJob 或 Lock4j
继续为 `DEFER` 时记录“不适用”，不得阻断 G4。

**阶段门禁：G4**

## 7. 长期候选能力
